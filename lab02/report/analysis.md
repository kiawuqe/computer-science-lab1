\# Лабораторная работа №2

\## Анализ веб-приложения и клиент-серверного взаимодействия



\## 1. Исследуемая информационная система

\* \*\*Сервис:\*\* Notion (notion.so)\[cite: 20]

\* \*\*Сценарий:\*\* Создание новой страницы и добавление текстового блока\[cite: 20].

\* \*\*Цель работы:\*\* Исследовать HTTP-взаимодействие между браузером и сервером, структуру запросов/ответов, использование cookies и работу API\[cite: 28].



\## 2. Анализ HTTP-запросов

\* \*\*Наблюдаемый факт:\*\* При открытии и работе с приложением в панели DevTools (вкладка Network) фиксируется интенсивный обмен данными по протоколу HTTPS\[cite: 30].

\* Используются следующие HTTP-методы:

&#x20; \* `GET` — для загрузки статических ресурсов (скрипты, стили, иконки) и начального состояния страниц.

&#x20; \* `POST` — основной метод для отправки пользовательских действий, сохранения блоков, синхронизации и запросов к API.

\* Примеры вызываемых URL: `https://www.notion.so/api/v3/loadPageChunk`, `https://www.notion.so/api/v3/saveTransactions`.



!\[Список запросов](../images/screenshots/net\_list.png)



\## 3. Анализ HTTP-ответов

\* \*\*Наблюдаемый факт:\*\* В ответ на клиентские запросы сервер возвращает HTTP-ответы со статусом `200 OK` (успешно) илиредко `4xx` при ошибках валидации.

\* \*\*Тип данных:\*\* Основной формат передачи данных между клиентом и сервером — `application/json`.

\* \*\*Заголовки ответа:\*\* Содержат параметры кэширования (`cache-control`), кодировку (`content-encoding: br`), а также защитные заголовки безопасности.

\* Браузер получает структурированный JSON-объект, на основе которого фронтенд обновляет дерево элементов страницы.



\## 4. Анализ параметров и передаваемых данных

\* \*\*Наблюдаемый факт:\*\* При выполнении сценария (создание блока) в теле (`Request Payload`) POST-запроса передаются структурированные данные.



!\[Тело запроса](../images/screenshots/net\_action.png)



\* \*\*Передаваемые параметры:\*\*

&#x20; \* Уникальные идентификаторы (`blockId`, `spaceId`, `userId`).

&#x20; \* Тип создаваемого элемента (например, `text`, `to\_do`).

&#x20; \* Текстовое содержимое блока (введенная строка).

\* \*Предположение:\* Сервер принимает эти данные, проверяет права пользователя через сессию и записывает транзакцию в базу данных.



\## 5. Анализ cookies

\* \*\*Наблюдаемый факт:\*\* Во вкладке Application -> Cookies для домена `notion.so` хранятся служебные идентификаторы сессии.



!\[Cookies](../images/screenshots/cookies.png)



\* \*\*Параметры cookies:\*\*

&#x20; \* `token\_v2` — основной токен авторизации пользователя (значение скрыто в целях безопасности согласно требованиям методички\[cite: 31]).

&#x20; \* Срок действия: долгосрочный (установлен с запасом в несколько месяцев/лет для персистентной авторизации).

&#x20; \* Флаги безопасности: критические куки защищены флагами `HttpOnly` (защита от перехвата через JS) и `Secure` (передача только по HTTPS).

\* \*\*Назначение:\*\* Обеспечение авторизации пользователя и поддержание активной сессии без необходимости повторного ввода пароля при каждом запросе.



\## 6. Взаимодействие Frontend, API и Backend

\* \*\*Пошаговый разбор сценария:\*\*

&#x20; 1. \*\*Действие пользователя:\*\* Пользователь нажимает кнопку создания страницы и вводит текст.

&#x20; 2. \*\*Интерфейс (Frontend):\*\* Обрабатывает событие ввода, отрисовывает элемент на экране (Optimistic UI).

&#x20; 3. \*\*HTTP-запрос:\*\* JavaScript формирует JSON-пакет и отправляет `POST`-запрос через fetch-API.

&#x20; 4. \*\*API / Backend:\*\* Принимает запрос, проверяет валидность токена из cookies, выполняет бизнес-логику.

&#x20; 5. \*\*Хранилище:\*\* Данные фиксируются в персистентной базе данных сервера.

&#x20; 6. \*\*HTTP-ответ:\*\* Сервер возвращает подтверждение (`200 OK`), завершая цикл синхронизации.
